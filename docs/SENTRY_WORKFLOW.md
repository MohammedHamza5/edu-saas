# Sentry Error Triage & Resolution Protocol
## بروتوكول فحص وحل أخطاء Sentry مع الذكاء الاصطناعي (منصة EduSaaS)

> **قاعدة ذهبية صارمة وغير قابلة للتفاوض:**
> **ممنوع منعاً باتاً على وكيل الذكاء الاصطناعي (AI Agent) تعديل أي كود، أو مساس أي ملف، أو تطبيق أي حل برمجياً أثناء مرحلة فحص وتشخيص أخطاء Sentry، إلا بعد الحصول على موافقة صريحة ومكتوبة من المطور (مثل: "موافق"، "نفّذ"، "Proceed").**

---

## 1. مراحل الفحص والحل الإلزامية (The 4-Phase Lifecycle)

عند توجيه الذكاء الاصطناعي لفحص أخطاء المنصة، يجب عليه الالتزام بدقة بالمراحل الأربع التالية بالتسلسل:

### 🔹 المرحلة الأولى: الجلب والتصنيف (Fetch via Sentry MCP)
1. الاتصال بـ Sentry عبر خادم Sentry MCP أو الـ API الرسمي لمنظمة `edsentre` ومشروع `flutter`.
2. حصر المشاكل غير المحلولة (`status: unresolved`).
3. استبعاد أخطاء الاختبارات والتجارب الداخلية والتركيز على أخطاء المستخدمين والإنتاج.
4. ترتيب الأخطاء حسب الأولوية وتكرار الحدوث (`Priority / Event Count`).

---

### 🔹 المرحلة الثانية: التشريح والشرح الفني الواضح (Diagnostic & Root Cause)
يقوم الذكاء الاصطناعي بتقديم تقرير مفصل ومنظم لكل خطأ بالشكل التالي:

1. **معرّف الخطأ وعنوانه:**
   - رقم المشكلة ورابطها المباشر على Sentry (مثل `FLUTTER-12`).
2. **أين وقع الخطأ بدقة؟ (Location):**
   - تحديد الملف ورقم السطر والـ Widget أو الـ Cubit المعني.
3. **لماذا حدث الخطأ؟ (Root Cause Analysis):**
   - شرح السبب الجذري للاستثناء بلغة تقنية دقيقة وسهلة الفهم (مثل: Null Assertion، فك استجابة غير متطابقة، انقطاع شبكة غير معالج، مشكلة في الـ Token).
4. **مسار المستخدم المؤدي للخطأ (User Journey & Breadcrumbs):**
   - ما الذي كان يفعله الطالب أو المدرس قبل وقوع الخطأ مباشرة.
5. **مستوى الخطورة والأثر (Severity & Impact):**
   - هل يعطل مساراً حرجاً (دفع / تسليم امتحان / تسجيل دخول) أم هو خطأ تجميلي عابر؟

---

### 🔹 المرحلة الثالثة: خطة الحل المقترحة والتوقف الإلزامي (Action Plan & Hard Stop)
يقترح الذكاء الاصطناعي خطة الحل دون كتابة أي كود:

1. **الملفات المستهدفة بالتعديل:** قائمة محددة بالملفات فقط دون إحداث Refactor جانبي.
2. **ملخص التعديل المقترح:** كيف سيتم علاج المشكلة جذرياً مع الالتزام بقواعد المشروع:
   - الالتزام بنمط Cubit و Pure Constructor Injection.
   - احترام RLS وكون بيانات العميل غير موثوقة.
   - معالجة حالات الـ UI الأربع (`Loading`, `Empty`, `Error`, `Success`).
   - حفظ التدويل (Localization) بدون نصوص ثابتة.
3. **المخاطر المحتملة (Risk Assessment):** هل يؤثر التعديل على شاشات أخرى؟
4. **⛔ بوابة التوقف الإلزامية (Hard Gate):**
   - **يتوقف الذكاء الاصطناعي فوراً** عند نهاية هذا القسم، ويوجه السؤال للمطور:
     > *"هذه هي خطة حل المشكلة [ID]. بانتظار موافقتك الصريحة للبدء في كتابة التعديل الفعلي."*

---

### 🔹 المرحلة الرابعة: التنفيذ والتحقق (فقط بعد موافقة المطور)
بمجرد كتابة المطور "موافق" أو "نفذ":
1. تطبيق أصغر تعديل دقيق يحقق الهدف فقط.
2. تشغيل الفحص الآلي الإلزامي:
   ```bash
   flutter analyze
   ```
3. التأكد من خلو المشروع تماماً من أي Lint أو Type Errors.
4. تحديث حالة المشكلة في Sentry إلى **Resolved** (عبر الـ API أو MCP).

---

## 2. أوامر سريعة لتوجيه الذكاء الاصطناعي (Magic Prompts)

يمكنك توجيه الذكاء الاصطناعي في أي وقت باستخدام إحدى هذه العبارات السريعة:

| الغرض | العبارة التي تكتبها للشات |
|---|---|
| **فحص شامل للأخطاء** | *"افحص أخطاء Sentry الحالية واشرح لي المشاكل مع خطة الحل طبقاً لـ SENTRY_WORKFLOW.md دون تعديل الكود."* |
| **فحص خطأ محدد برقم الـ ID** | *"راجع الخطأ FLUTTER-X في Sentry واشرح سببه الجذري وخطة علاجه."* |
| **الموافقة على بدء الحل** | *"موافق على خطة الخطأ FLUTTER-X، نفذ الحل البرمجي الآن ثم تحقق من الـ analyzer."* |
| **إغلاق المشكلة في Sentry** | *"تم التحقق من الإصلاح، قم بتعليم FLUTTER-X كـ Resolved في Sentry."* |

---

## 3. قيود إضافية خاصة بالمشروع
- لا يجوز استخدام `try/catch` فارغة أو صامتة لتجاوز الخطأ؛ الحل يجب أن يعالج السبب الجذري.
- الأخطاء المتعلقة بـ Supabase RLS أو Edge Functions تُعالج في الطبقة المناسبة لها وفقاً لوثيقة `03_ARCHITECTURE_MASTER.md`.
