## 1. جوهر وفلسفة المنصة (Platform DNA)
المنصة مبنية بنظام **White-Label Multi-Tenant SaaS** من اليوم الأول.
- **الهدف الأسمى:** خدمة مئات المدرسين والأكاديميات التعليمية (التركيز الحالي: النظام الأمريكي SAT / ACT / EST)، بحيث يحصل كل مدرس على منصة خاصة به بالكامل، بهويته، دومينه، شعاره، ألوانه، طلّابه، وامتحاناته المستقلة، دون تداخل حرف واحد مع أي مدرس آخر.
- **المصدر الموحد للكود (Single Codebase):** كود فلاتر موحد واحد (`lib/`) يخدم جميع المدرسين والديمو، وتحديد هوية المدرس يتم لحظياً في 0 ملي ثانية عبر الدومين (`window.location.hostname`).

## 2. خريطة العزل المعماري الحالية (Isolation Architecture)

```text
                                [ User Access ]
                                       │
                ┌──────────────────────┴──────────────────────┐
        (demo.edsentre.com)                       (antounios.edsentre.com)
                │                                             │
      [antounios-test Site]                         [antounios Site]
       (Firebase Hosting)                          (Firebase Hosting)
                │                                             │
      TenantResolver:                               TenantResolver:
   11111111-1111-...                             ea5caf8b-112f-...
 (معلم تجريبي - معاينة المنصة)                        (د. أنطونيوس أشرف)
                │                                             │
                └──────────────────────┬──────────────────────┘
                                       │
                      [ Supabase PostgreSQL + RLS ]
        auth.uid() ──> public.users.tenant_id ──> Strict RLS Enforcement
                       (Zero Cross-Tenant Data Leakage)
```

1. **الاستضافة (Frontend Hosting):** مواقع استضافة معزولة لكل بيئة أو مدرس عبر Firebase Hosting (`antounios` و `antounios-test`).
2. **قاعدة البيانات (Database & RLS):** عزل حتمي عبر `tenant_id` مع سياسات Row Level Security، بحيث يشتق السيرفر الهوية من `auth.uid()` حصراً. عميل Flutter غير موثوق به أبدًا.
3. **الهوية البصرية (Theme & Profile Injection):** لا توجد أي شروط `if / else` للهوية في الشاشات. الشاشات تقرأ من كائن `TenantBranding` المحقون عبر `TenantThemeCubit`.

## 3. التدقيق الفني الشامل: 7 مشاكل محتملة عند كثرة المدرسين وحلولها

قبل إضافة مدرسين جدد والتوسع، هذا هو التشريح الدقيق للمشاكل التي قد تحدث مستقبلاً وكيفية تفاديها:

---

### 🚨 المشكلة الأولى: تصادم البريد الإلكتروني للطلاب (Cross-Tenant Student Email Collision)
- **المشكلة:** في نظام Supabase Auth الافتراضي، عمود `email` في جدول `auth.users` فريد عالمياً (Globally Unique). لو سجل طالب ببريده `student@gmail.com` عند المدرس (أ) لدراسة SAT، ثم أراد نفس الطالب الانضمام للمدرس (ب) لدراسة EST، سيظهر له خطأ: *"هذا الحساب مسجل مسبقاً"*.
- **الأثر:** يمنع الطالب من دراسة مادتين مع مدرسين مختلفين بنفس الإيميل، أو يدفع الطالب لإنشاء إيميل وهمي لكل مدرس.
- **الحل المقترح (بدون فوضى):**
  - **الخيار أ (موصى به لـ V1):** السماح بتسجيل الدخول المركزي (Single Sign-On): حساب الطالب في `auth.users` يظل واحداً، لكن يربط بجدول وسيط `student_tenants` أو `group_members` يسمح للطالب بالانتماء لأكثر من أكاديمية والتبديل بينها بسلاسة عبر القائمة.
  - **الخيار ب (الفصل التام):** إنشاء بادئة للمستأجر في الإيميل المخفي داخلياً (`student+tenantA@domain.com`) لو رغبنا في عزل الحسابات 100%.

---

### 🚨 المشكلة الثانية: التسجيل اليدوي للهوية في الكود (`TenantRegistry` Static Hardcoding)
- **المشكلة:** حالياً، تسجيل مدرس جديد وتحديد اسمه ولونه ولوجوه يتم عبر خريطة ثابتة باليد في كود دارت:
  `lib/core/config/tenant_registry.dart`
  عند انضمام المدرس الخامس أو العاشر، ستضطر لتعديل ملف دارت، وتشغيل `flutter build web`، ثم رفعه.
- **الأثر:** بطء إضافة المدرسين واحتياج تدخل مبرمج لكل مدرس جديد.
- **الحل المقترح:**
  - تحويل `TenantResolver` ليقرأ الهوية ديناميكياً من جدول `public.tenants` الموجود بالفعل في قاعدة البيانات، مع كاش فوري في `AppCache` و `SecureStorage`.
  - **النتيجة:** يمكنك إضافة أي مدرس جديد في 30 ثانية من لوحة التحكم أو قاعدة البيانات بكتابة (اسمه، دومينه، ألوانه، ورابط لوجوه)، وسيتعرف عليه تطبيق الويب فوراً دون إعادة بناء الكود نهائياً!

---

### 🚨 المشكلة الثالثة: استضافة الويب وبطاقات المشاركة للسوشيال ميديا (Social Media Meta Scraping)
- **المشكلة:** كما رأينا في رسائل الواتساب والماسنجر، روبوتات السوشيال ميديا (Facebook, WhatsApp) لا تشغل كود Flutter أو JavaScript، بل تقرأ ملف `index.html` الأولي الثابت.
- **الأثر:** لو لدينا 10 مدرسين، سنحتاج لتوليد 10 ملفات `index.html` أو 10 مواقع استضافة يدوياً في Firebase Hosting.
- **الحل المقترح:**
  - استخدام **Cloudflare Worker** خفيف جداً (Edge Worker) أمام الدومين الرئيسي:
    عندما يطلب زائر أو روبوت فيسبوك دومين `hossam.edsentre.com`، يقوم الـ Worker في 2 ملي ثانية بقراءة اسم ولون ولوجو الأستاذ حسام، ويحقن وسوم `<meta property="og:title">` قبل إرجاع الصفحة.
  - **النتيجة:** بناء كود واحد فقط لجميع المدرسين في العالم مهما بلغ عددهم، وبطاقات السوشيال ميديا تعمل 100% بدقة لكل مدرس.

---

### 🚨 المشكلة الرابعة: عزل التخزين والملفات المرفوعة (Storage Bucket Prefix Isolation)
- **المشكلة:** ملفات المذكرات، وصور الامتحانات، وواجبات الطلاب تُرفع على Supabase Storage.
- **الأثر:** لو رُفعت الملفات في مسار مسطح عام، قد يتمكن مستخدم خبيث يملك رابط ملف من الوصول لمذكرات مدرس آخر.
- **الحل المقترح:**
  - فرض نمط المسارات الإلزامي في كل رفع:
    `materials/{tenant_id}/{folder_id}/{filename}`
    `submissions/{tenant_id}/{assignment_id}/{student_id}/{filename}`
  - كتابة سياسة RLS صارمة في الـ Storage تمنع أي قراءة أو كتابة لملف إلا إذا طابق مساره `auth_tenant_id()`.

---

### 🚨 المشكلة الخامسة: تنظيم فيديوهات Bunny Stream بين المدرسين
- **المشكلة:** فيديوهات المنصة الحالية ترتبط بمكتبة Bunny Stream واحدة (`BUNNY_LIBRARY_ID=770018`).
- **الأثر:** اختلاط ملفات الفيديو الخام على لوحة تحكم Bunny، وصعوبة حساب استهلاك الباندويث والمساحة لكل مدرس على حدة عند محاسبته.
- **الحل المقترح:**
  - إنشاء **Collection** مستقل داخل Bunny لكل مدرس يحمل الـ `tenant_id` الخاص به.
  - تخزين `bunny_collection_id` في جدول `tenants` لفرز الفيديوهات وحساب التكاليف بدقة وسهولة.

---

### 🚨 المشكلة السادسة: طلبات المدرسين الخاصة وفوضى الـ `if / else` (Custom Features Matrix)
- **المشكلة:** مدرس يطلب ميزة خاصة جداً (مثل: نظام حساب غياب مختلف، أو حاسبة محددة، أو نظام امتحانات مخصص)، ومدرس آخر يرفضها تماماً.
- **الأثر:** تحول شاشات التطبيق لغابة من شروط `if (teacher == 'x')`.
- **الحل المقترح الصارم:**
  1. **مصفوفة مفاتيح الميزات (Feature Toggles Matrix):** الميزات البرمجية تُعطى أسماء وظيفية عامة تُحفظ في إعدادات المدرس (`settings: { "enable_calculator": false, "pdf_only_homework": true }`). الشاشة تسأل عن الإعداد وليس عن اسم المدرس.
  2. **فروع Git المعزولة (Git Branches) للحالات المتطرفة:** إذا طلب مدرس تغييراً جذرياً في منطق البزنس يتعارض مع باقي المنصة، يتم إنشاء فرع مخصص له `feature/tenant-[name]` لحماية الفرع الرئيسي `main`.

---

### 🚨 المشكلة السابعة: عزل الإشعارات والتنبيهات (FCM Push Scoping)
- **المشكلة:** عند إرسال تنبيه أو إشعار جماعي، يجب ضمان عدم وصوله لطلاب أي مدرس آخر.
- **الحل المقترح:**
  - تسجيل التوكنات في FCM باستخدام Topics مشفرة بالـ `tenant_id`:
    `topic: tenant_{tenant_id}_all`
    `topic: tenant_{tenant_id}_group_{group_id}`

## 4. ميثاق تشغيل الوكيل البرمجي (AI Agent Protocol)
- **قاعدة عدم التعديل العشوائي (Zero Blind Edits):** يُمنع منعاً باتاً التعديل في أي جدول أو منطق RLS أو بنية الـ Multi-Tenancy إلا بعد استشارة المطور وعرض الخيارات والحصول على موافقة صريحة مكتوبة.
- **فصل الديمو عن الإنتاج:** أي اختبارات أو مبيعات تجري حصرياً داخل نطاق المستأجر `11111111-1111-1111-1111-111111111111` وعلى استضافة `antounios-test`، ويحظر مساس بيئة الإنتاج الخاصة بدكتور أنطونيوس.
